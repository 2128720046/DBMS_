# DBMS 项目模块介绍文档

## 1. 文档目的
本文档用于统一说明本项目各模块职责、边界和目标，帮助团队快速理解“每个模块做什么、做到什么程度算完成”。

## 2. 系统分层与总体职责

### 2.1 前端展示层（frontend）
职责：
- 负责页面展示、用户交互、路由跳转、状态反馈。
- 调用后端 API，展示操作结果。
- 处理加载态、错误态、空数据态。

目标：
- 至少完成数据库管理、表管理、记录管理三类页面。
- 页面可演示完整主流程（查询、提交、反馈）。
- 与后端接口联调成功，错误提示清晰。

### 2.2 控制器层（controller）
职责：
- 接收 HTTP 请求，完成路径映射、参数绑定、基础参数校验。
- 调用应用层服务，不直接实现复杂业务逻辑。
- 统一返回 `ApiResponse`。

目标：
- API 路径语义清晰。
- 请求参数校验完善。
- 所有响应格式统一。

### 2.3 应用层（application）
职责：
- 负责编排用例流程，协调多个业务模块执行顺序。
- 处理跨模块调用、错误传播和结果聚合。
- 作为控制器层与业务层之间的“流程中枢”。

目标：
- 每个核心用例都在应用层有清晰入口。
- 调用链稳定，模块间依赖明确。
- 出错时能返回可定位的问题信息。

### 2.4 业务层（domain）
职责：
- 负责业务规则和领域逻辑。
- 包括元数据规则、记录规则、索引规则、完整性规则、事务规则、安全规则、备份规则。
- 不处理具体存储细节，只定义“该做什么”。

目标：
- 规则实现可测试、可复用。
- 不依赖前端或控制器细节。
- 规则失败时提供明确原因。

### 2.5 基础设施层（infrastructure）
职责：
- 负责文件读写、日志落盘、备份恢复、网络适配等底层实现。
- 为业务层提供仓储能力和外部资源访问能力。

目标：
- 文件结构可维护，读写可靠。
- 出错可追踪（日志完整）。
- 支撑业务层稳定运行。

### 2.6 公共模型层（model）
职责：
- 定义业务对象和参数对象（数据库、表、字段、记录、约束、索引、会话、备份等）。
- 统一跨层传参结构。

目标：
- 字段定义清晰、命名统一。
- 避免重复定义同类对象。

### 2.7 公共能力层（common）
职责：
- 提供统一返回结构、通用工具、公共常量。
- 保证前后端对响应协议理解一致。

目标：
- 所有接口统一成功/失败语义。
- 通用结构集中维护，避免散乱。

## 3. 业务模块详细说明（按后端模块）

### 3.1 元数据管理模块
对应：`application/DatabaseApplicationService`、`application/TableApplicationService`、`application/FieldApplicationService`、`domain/MetadataService`、`infrastructure/DatabaseMetaRepository`、`TableMetaRepository`、`SchemaRepository`

负责功能：
- 数据库、表、字段、约束元信息的创建、读取、更新、删除。
- 维护数据库描述文件、表描述文件、字段定义文件、约束文件。

需达成目标：
- 数据库和表的结构信息可持久化。
- 结构变更后，相关元数据一致。
- 元数据接口可被前端管理页面稳定调用。

### 3.2 数据管理模块
对应：`application/RecordApplicationService`、`domain/RecordService`、`infrastructure/RecordRepository`

负责功能：
- 记录插入、查询、更新、删除。
- 条件查询、结果组装、执行条数统计。

需达成目标：
- 记录操作具备正确性和可观测性。
- 查询性能在课程项目规模内可接受。
- 对异常输入有明确错误提示。

### 3.3 索引管理模块
对应：`application/IndexApplicationService`、`domain/IndexService`、`infrastructure/IndexRepository`

负责功能：
- 索引创建、删除、重建、查询。
- 记录变化时同步维护索引。

需达成目标：
- 至少支持单字段基础索引。
- 能在查询流程中被调用并返回定位结果。
- 索引文件与记录文件保持一致性。

### 3.4 完整性管理模块
对应：`application/IntegrityApplicationService`、`domain/IntegrityService`、`infrastructure/SchemaRepository`、`RecordRepository`

负责功能：
- 主键、外键、唯一、非空、默认值、自增等规则校验。
- 在插入/更新前执行拦截校验。

需达成目标：
- 非法数据不能写入记录文件。
- 失败原因可读、可定位。
- 规则定义与执行逻辑一致。

### 3.5 事务管理模块
对应：`application/TransactionApplicationService`、`domain/TransactionService`、`infrastructure/LogRepository`

负责功能：
- 事务开启、提交、回滚、状态查询。
- 操作日志记录和异常恢复。

需达成目标：
- 多步操作失败时可回滚。
- 事务日志可追踪。
- 提交/回滚结果明确。

### 3.6 安全管理模块
对应：`application/SecurityApplicationService`、`domain/SecurityService`、`infrastructure/UserRepository`

负责功能：
- 登录、登出、用户管理、权限校验。
- 会话上下文维护。

需达成目标：
- 登录鉴权流程可用。
- 权限不足时准确拦截。
- 用户数据和权限配置可持久化。

### 3.7 备份恢复模块
对应：`application/BackupApplicationService`、`domain/BackupService`、`infrastructure/BackupRepository`

负责功能：
- 数据库备份、恢复、备份列表、备份删除。
- 必要时结合日志文件恢复状态。

需达成目标：
- 备份可生成且可恢复。
- 恢复后系统可继续运行。
- 备份操作有完整结果反馈。

### 3.8 客户端通信模块
对应：`application/ClientApplicationService`、`domain/ClientService`、`infrastructure/NetworkAdapter`

负责功能：
- 客户端连接、断开、请求收发。
- 作为扩展能力接入远程调用。

需达成目标：
- 保持基础连接可用。
- 为后续扩展预留接口和结构。

## 4. 模块协作边界（必须遵守）
- 控制器层不直接调用仓储层。
- 应用层不直接操作具体文件。
- 业务层只依赖接口，不依赖实现细节。
- 基础设施层不承载业务规则判断。
- 所有模块统一使用 `ApiResponse` 返回协议。

## 5. 每个模块“完成”的判定标准
- 有可调用入口（Controller 或 Service）。
- 有明确输入输出对象（DTO/Model）。
- 有最小可用实现（不是空方法）。
- 有成功与失败两类可观测结果。
- 能通过至少 1 个联调用例验证。

## 6. 第一轮重点模块建议
第一轮优先保证：
1. 元数据管理模块
2. 数据管理模块（先查询、后写入）
3. 前端数据库管理与表管理页面

第一轮可后置：
1. 事务深度实现
2. 客户端通信高级能力
3. 复杂权限模型
