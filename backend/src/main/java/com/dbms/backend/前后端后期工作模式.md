
# 前后端后期工作模式（SQL-only 版本）

本文档用于规划后期前后端工程师的协作方式、迭代流程与扩展路线，适配当前 SQL-only 后端架构。

---

## 1. 总体目标

1. 保持对外接口只保留 SQL 执行入口（/api/sql/execute）。
2. 前端通过 SQL 驱动所有页面操作，后端解析 SQL 并落地到二进制存储引擎。
3. 在不破坏现有能力的前提下，逐步扩展 SQL 子集与引擎功能。

---

## 2. 角色分工

### 前端工程师
1. 负责 UI/交互与 SQL 生成策略。
2. 维护统一的 SQL 构建工具（例如 sqlBuilder.ts），避免页面内散落拼 SQL。
3. 对每个功能按钮提供对应 SQL 模板，并维护示例用例。
4. 管理接口调用协议（/api/sql/execute 的请求体与返回处理）。

### 后端工程师
1. 维护 SQL 解析层（SqlParser）与执行层（SqlExecutor）。
2. 维护应用服务层（Database/Table/Record ApplicationService）。
3. 维护二进制引擎文件格式与读写逻辑（Native*GatewayImpl）。
4. 提供 SQL 子集能力说明与边界约束（README + 变更日志）。

---

## 3. 协作流程（每个需求）

1. 前端提出需求与页面行为：例如“新增索引管理”。
2. 后端评估 SQL 扩展范围：是否新增 SQL 子命令。
3. 双方确认 SQL 语法与请求协议。
4. 后端实现：Parser -> Command -> Executor -> Gateway。
5. 前端实现：SQL 构建 -> 调用 /api/sql/execute。
6. 联调：基于 Swagger 或 Postman 对 SQL 逐条验证。
7. 更新文档：README、SQL 子集说明、前端 SQL 模板清单。

---

## 4. SQL-only 协议约定

### 请求体
```
{
	"databaseName": "test_db",
	"sql": "SELECT * FROM users"
}
```

### 返回体（统一响应）
- message 类型：
```
{
	"code": 200,
	"message": "执行成功",
	"data": {
		"type": "message",
		"status": "success",
		"data": "表创建成功",
		"affectedRows": 1,
		"refreshTree": true
	}
}
```

- table 类型：
```
{
	"code": 200,
	"message": "执行成功",
	"data": {
		"type": "table",
		"status": "success",
		"columns": [{"prop":"ID","label":"ID"}],
		"data": [{"ID":1}],
		"affectedRows": 1
	}
}
```

## 4.1 Swagger 使用方式

1. 启动后端（开发环境）：
```
mvn spring-boot:run
```
2. 访问 Swagger UI：
- http://localhost:8080/swagger-ui/index.html
3. 选择接口：`POST /api/sql/execute`
4. 填写请求体 JSON 并执行：
```
{
	"databaseName": "test_db",
	"sql": "SHOW DATABASES"
}
```
5. 查看返回结果，确认 type=message 或 type=table。

注意：生产环境默认关闭 Swagger（application-prod.yml）。

## 5. 前端 SQL 构建规范

1. 所有 SQL 语句统一由一个模块生成（禁止在页面拼字符串）。
2. 变量统一做基础转义（字符串 -> 单引号包裹，内部单引号双写）。
3. 表名、列名等标识符统一做合法性校验（字母开头 + 字母数字下划线）。
4. INSERT 必须指定字段列表（与后端约束保持一致）。
5. UPDATE/DELETE 仅使用 AND + = 等值条件，避免使用不支持的语法。

---

## 6. 后端扩展路线

### 6.1 SQL 解析扩展
1. 在 SqlParser 中新增识别语句类型。
2. 在 SqlCommand 中新增结构化命令。
3. 在 SqlExecutor 中新增执行分支。

### 6.2 存储引擎扩展
1. 表结构扩展：新增字段属性写入 .tdf。
2. 记录层扩展：新增数据类型、索引或压缩。
3. 索引层扩展：新增 .ix 文件读写。

---

## 7. 推荐的功能迭代顺序

1. SELECT 条件能力增强（LIKE/IN/范围）。
2. CREATE INDEX / DROP INDEX。
3. ALTER TABLE 的数据迁移（同步更新 .trd）。
4. 事务基础支持（简单锁/单表事务）。
5. 备份与恢复能力（快照/增量）。

---

## 8. 联调与测试策略

1. 每新增一条 SQL 语法，必须提供最少 2 组用例：成功 + 失败。
2. 后端增加 parser/executor 单测（如果暂时不写测试，至少提供 SQL 手工验证清单）。
3. 前端基于 SQL 模板清单做回归。

---

## 9. 文档与变更管理

1. README 保持 SQL 子集说明同步更新。
2. 每次新增语法必须写清楚“支持范围 + 限制”。
3. 对外版本号与 SQL 子集版本保持一致（如 v0.2 扩展 INDEX）。

---

## 10. 常见协作冲突与处理

1. 前端需要语法，后端暂不支持：
	 - 先收敛到最小可行语法，后续增强。
2. 后端新增语法，前端未对接：
	 - 先写在文档与 Swagger 中，按版本迭代。
3. SQL 解析与引擎实现不一致：
	 - 以后端执行结果为准，前端不得假设 SQL 成功。

---

## 11. 交付标准

1. 每个新功能必须包含：SQL 语法、解析逻辑、执行逻辑、前端调用示例。
2. 必须提供最少一组端到端验证 SQL。
3. README 与 SQL 清单同步更新。
